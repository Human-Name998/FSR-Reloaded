### FSR4 crash — "allocator Reset FAILED" storm then heap corruption (0xC0000374)
- **Root cause**: after the jaggedfix deploy, the 16:56 session crashed. The `fsr4_diag.log` tail proved the chain: `g_ffxDispatch` threw `0xe06d7363` (the deterministic FSR4-SDK-with-FG-context crash on the Radeon 860M), and the FSR4 SEH crash handler then did `Close()` + `ExecuteCommandLists()` on the **partially-recorded command list** — submitting corrupted GPU commands → AMD driver GPU timeout → TDR → `DXGI_ERROR_DEVICE_REMOVED` (`hr=0x887a0005` on the next `CreateRootSignature`/`CreateCommittedResource`). After removal, every D3D12 call fails (`allocator Reset FAILED hr=0x80004005` storm; `ensureInitialized()` returns cached READY without ever calling `GetDeviceRemovedReason`), and Java's bypass-active branch swallowed every failure (no suspension/hard-disable), so the loop spun — pool recreates failing `0x887a0005` ×7, device rebuild, crash again — until the process died with `STATUS_HEAP_CORRUPTION`.
- **Fix (3 native + 1 Java)**: (1) new `D3D12Device::recreateCommandResources()` — discards + recreates the round-robin allocator pair + command list, zeroing per-allocator fence bookkeeping; (2) the FSR4 `__except` handler calls it instead of Close+Execute — no GPU submit, no fence signal (nothing was submitted; advancing without executing would store a never-signaled fence value the next pre-dispatch wait would hang on), and the bilinear bypass (armed) takes over next frame; (3) the FG `generate` crash path had the same latent submit-after-crash — it now Detaches the corrupted allocator+list exactly like the `prepare` path already did (next `prepare` reinitializes and recreates them); (4) Java's bypass branch gained `fsr4BypassFailStreak` — the first bypass failure (the SDK crash frame itself) stays lenient, but a healthy device makes the bypass dispatch succeed every frame, so N consecutive bypass failures mean device removal → after `FSR4_MAX_CONSECUTIVE_DISPATCH_FAILURES` (5) it suspends + hard-disables to the D3D12-free FSR1 spatial render instead of spinning until heap corruption; reset on a successful dispatch.
- **Second fix (17:17, "now it just freezes at the first frame"):** the first fix's `recreateCommandResources()` RELEASED the recording-state command list (`Reset()`), which is a D3D12 contract violation — on the AMD driver it corrupted the runtime's allocator bookkeeping so `createCommandAllocator` failed, leaving the allocator pair NULL. Every subsequent dispatch then faulted (SEH-caught), Java's new bypass fail-streak correctly hard-disabled to FSR1, but FG stayed active and hammered the broken device — `nativeFinish`'s 5000ms fence wait stalled the render thread ~5s/frame (the freeze; game log shows the disable at 17:10:29 then no render activity until quit at 17:10:37). Fixed: (1) `recreateCommandResources()` now **Detaches** the list + allocators (leaked to process exit — the FG-proven "Detach not Reset" pattern) so the recreate succeeds on the healthy device and the bilinear bypass takes over next frame; (2) dispatch guards against a null allocator (clean failure → streak → FSR1 instead of a fault); (3) `fgActive()` is now gated on `!fsr4HardDisabled` so a hard-disabled session degrades to the D3D12-free FSR1 spatial render with FG off (no more 5s stalls).
- **Third fix (17:34, "it is still just frozen"):** the second fix was right but incomplete — new HRESULT logging showed `createCommandAllocator[0] FAILED hr=0x887a0005` = **DXGI_ERROR_DEVICE_REMOVED**. The FSR4 SDK's dispatch throw *itself* removes the D3D12 device once an FG context exists on this iGPU, so the post-crash bypass (D3D12) could never run and every FSR4+FG session collapsed to FSR1 (which at 0.25 scale looks frozen). The arm-after-crash design can't work here. - **Fourth fix (17:44, "still completely frozen … game runs fine in background"): FG is not viable on this GPU at all.** The 17:38 diag proved it even with the pre-arm: no FSR4 SDK crash (bypass armed, SDK never dispatched), yet CPU-only `CreateRootSignature` returned `DXGI_ERROR_DEVICE_REMOVED 0x887a0005` — the device was already gone before the first dispatch. So the FG `ffxCreateContext` itself removes the D3D12 device when coexisting with the FSR4 context. Every variant dies: FSR4-SDK+FG (crash+removal), pre-armed-bilinear+FG (removal), so no D3D12 recovery helps. Fix: **never create the FG context on an AMD iGPU** — `maybeDisableFgOnIgpu()` (both FSR4 init sites) sets `fgIgpuUnsupported` → `fgActive()` false → FG never initializes → the session runs **plain real FSR4** (real temporal upscale, no crash, no device removal), with a clear one-time warn. ### FSR4 jagged diagonal edges even at low render scale — DEPTH_INVERTED regression + jitter contract restored ("fsr 4 edges are jagged when diagonal and not smooth")
- **Root cause #1 — the SDK was told the depth is REVERSED-Z**: the 1.21.11 port re-added `FFX_UPSCALE_ENABLE_DEPTH_INVERTED` to the FSR4 context flags — but the depth written into the shared pool (DEPTH_COPY_CS / VK MV-gen) is NON-reversed (near→0, far→1), exactly what the validated Aug 6 baseline removed the flag for: "telling the SDK the depth is inverted makes it linearize depth backwards: every pixel lands on the far plane, the whole image is treated as sky/disoccluded, and the SDK discards all history each frame → no temporal accumulation". With the constant-0.5 depth fallback the flag was a no-op, so it stayed invisible until the 2026-08-29 Iris depth-version fix started writing REAL per-pixel depth into the proxy → `probeFsr4Depth` enables `uUseDepth=1` → non-reversed depth hits an inverted context → the SDK rejects ALL history every frame → the upscale degrades to pure spatial → jagged diagonals at ANY scale. `fsr4_context.cpp` now uses `FFX_UPSCALE_ENABLE_AUTO_EXPOSURE` only (validated baseline).
- **Root cause #2 — jitter pass-through was broken on the GL path**: the render jitters ±0.5 render px (Halton) but the GL FSR4 dispatch passed `(0,0)` to the SDK (the 2026-08-30 "revert" band-aid). The SDK then assumes every frame is on the same grid — its history reads are off by the per-frame jitter delta (up to ~1 render px = up to 4 display px at 25% scale), beyond the neighborhood clamp → history rejected → spatial output. The dispatch now passes the real `(jitterX, jitterY)`, and the missing native Y-SIGN fix is restored: `jitterOffset.y = -params.jitterY` in `fsr4_context.cpp` + `fg4_context.cpp` (DirectX NDC is +Y down, our OpenGL render is +Y up — the documented 2026-08-08 fix that was lost in the native-source recovery).
- **FG prepare got the same two fixes**: `prepareDesc.flags = 0` (was `FFX_FRAMEGENERATION_ENABLE_DEPTH_INVERTED`) and `prepareDesc.jitterOffset.y = -params.jitterY` — it consumes the same non-reversed pool depth and same render jitter.
- Deployed to the 1.21.11 instance 16:23 (backup `.bak-20260830-jaggedfix`). Expected: diagonal edges reconstruct smoothly from accumulated sub-pixel samples standing still, and history survives motion pans (no more spatial fallback look); the `[DIAG]` jitter line should show nonzero jitter with the pack consuming it, and the depth probe should log "REAL per-pixel depth" with `uUseDepth=1` now working correctly against the SDK.

### FSR4 crash-loop FREEZE — SECOND fix: reinit-success must NOT reset the hard-disable latch ("it still freezes on the GL instance")
- The first crash-loop fix (below) gated the `needsRecreate` device+pool rebuilds on `!fsr4HardDisabled` — but BOTH reinit-success blocks then cleared `fsr4DispatchFailCount`/`fsr4HardDisabled` ("clean slate after successful reinit"). The crash-loop IS "crash → device+pool rebuild success → crash → …": every successful rebuild wiped the counter, so the 5-strike escalation never latched, `needsRecreate` stayed open, and the expensive rebuild (the actual render-thread hang on a wedged AMD iGPU) kept firing forever. Verified against the diag log: the tail showed 5× `crash → full device+pool recreate`, counter never reaching the latch.
- **Fix**: both reinit-success blocks now PRESERVE `fsr4DispatchFailCount`/`fsr4HardDisabled`. Correct recovery is only a genuinely good dispatch (`fsr4DispatchFailCount = 0` on success) or a deliberate `markDirty()`/`applyAutoScale()`; a re-init that merely rebuilds then crashes again must not reset the escalation. The FG `fg4PermanentlyDisabled` clear on successful FG init stays (that is the separate FG catch-22 fix). This hardens the GL path (no VulkanMod needed — the crash is a shared-D3D12-layer fault, and the 1.21.11 instance is GL/Iris).
- Confirmed in the 10:23-10:24 GL session: a single `g_ffxDispatch` crash now lands in FSR1 fallback and stays there (clean, no freeze).

### FSR4 VKMod crash-loop FREEZE — "runs for a bit, then completely freezes while the game runs fine in the background"
- **Root cause**: the freeze was NOT an unbounded fence wait. The `fsr4_diag.log` (which keeps writing even while the render thread hangs) showed the VulkanMod path: `g_ffxDispatch` throws an MSVC C++ exception (`0xe06d7363`, an SDK `throw` — caught by the SEH `dispatchFsr4VkMod` handler and returned as `JNI_FALSE`), and each crash was followed by a FULL D3D12 device + 10-texture pool rebuild that repeated indefinitely (crash → recreate → crash), finally hanging the render thread on the AMD iGPU mid-recreate. That single 5-consecutive-failure latch (`fsr4HardDisabled`) existed ONLY on the GL dispatch site; the VulkanMod dispatch site silently ignored a failed dispatch and re-armed it every frame, so a genuinely broken SDK crash-looped without ever self-limiting.
- **Fix**: mirror the GL-path escalation into the VulkanMod dispatch site — consecutive `dispatchFsr4VkMod` failures (counted only when the queue copy was actually ready, so a transient saturated-queue timeout is NOT counted) now escalate to `fsr4HardDisabled = true` after 5; the VKMod dispatch gate gained `!fsr4HardDisabled`; both `needsRecreate` re-init blocks are gated on `!fsr4HardDisabled` so a hard-disabled session STOPS rebuilding the D3D12 device + pool (the hang); and `spatialFallbackActive()` gained `|| fsr4HardDisabled` so it routes to the D3D12-free FSR1 spatial render (fresh frames). The latch clears on a deliberate settings change (`markDirty()`/`applyAutoScale()`) or a successful re-init — a restart or a deliberate change is the user retrying. Self-limiting: genuine repeated crashes hard-disable to FSR1; transient queue timeouts do not.

### FG DX12 permanent-disable latch now clears on a deliberate settings change ("FSR3 FG DX12 says it is only running a spatial upscaler after a quality change")
- **Root cause / catch-22**: `noteD3D12RuntimeFailure()` sets `fg4PermanentlyDisabled = true` after `FG_MAX_RUNTIME_FAILURES` (3) failures, the latch was NEVER reset for the session, and it GATES the FG re-init (`fgActive()` → `!fg4PermanentlyDisabled`). A quality/version change tears down and re-initializes the FSR4 + FG D3D12 contexts; during that transition storm (context teardown + Iris recompile + deep GL queue) a few transient `doFrameGenDispatch` failures or waitIdle-stall watchdog hits rack up to 3 and permanently kill FG — degrading FG_DX12 to FSR1 spatial for the rest of the session and showing "Too many runtime failures" / the version pill as unavailable in the settings screen. Because the latch itself blocked the FG re-init, nothing could ever recover it short of a restart.
- **Fix**: a deliberate rebuild (`markDirty()` for version/Iris-quality changes, `applyAutoScale()` for the GL quality slider) now clears `fg4PermanentlyDisabled` + the `fgRuntimeFailCount`/`fgStallConsecutive` counters before tearing down, so the next re-init actually runs FG again. Belt-and-suspenders: a successful `Fg4Native.nativeInit` (both the GL and VulkanMod init sites) also clears the latch. Self-limiting: if the failures are genuine the latch re-engages as before — only the catch-22 is removed.

### FSR4/D3D12 context + shared pool are now PARKED on switch-away instead of torn down ("instead of tearing down the dx12 context every time")
- The D3D12 **device** already survived switches (disposeD3D12 only runs at full destroy()); what got torn down on switching away from FSR4/FG_DX12 was the **SDK context** (`ffxCreateContext`) + the **10-texture shared pool** — the expensive, crash-prone cross-API recreate (external-memory handle imports + GL import + ffxCreateContext are exactly the operations that fault the AMD driver when raced against pipeline churn).
- **Fix**: `markDirty()` (version switch away) and the per-frame "FSR4 not selected" branch now **park** the live context: keep the SDK context + pool alive, clear `fsr4Initialized` so nothing dispatches, keep the size sentinel. On re-select, the init blocks (both the GL and VulkanMod paths) call `unparkFsr4Context()`: if the parked dims + pool type (GL-imported vs D3D12-only) match the current renderer, it restores `fsr4Initialized` (and `fg4Initialized` for FG re-select), resets temporal history + dispatch state (first dispatch is reset=true, clearing the SDK's internal history), and **skips the entire init path — zero cross-API work**.
- Stale parked context (size changed while away, or renderer switched GL↔VKMod) is torn down properly (SDK context before pool — the documented shutdown order) and the normal init path runs. `destroy()` and `applyAutoScale()` use the new park-aware `teardownFsr4Context()` so a parked context can never leak or have its pool released under it (use-after-free guard).
- Result: a same-size FSR4 off→on toggle or FSR2→FSR4 switch is now **instant and crash-free** — no pool allocate, no imports, no ffxCreateContext. Only a size change while away pays the recreate.

### FSR2 ↔ FSR3 switch no longer recompiles the shared passes ("way of switching fsr version without rebuilding")
- **Root cause**: an FSR2↔FSR3 switch already does NOT rebuild the Iris/pack pipeline, but the mod's 6 upscale compute shaders were re-hashed per version because `ShaderBinaryCache` hashed the RAW GLSL (whitespace + comments included). The released FSR2/FSR3 shaders are byte-identical except ACCUMULATE (FSR3 adds `uShadingChange`, `FSR3_EPSILON`/`LOCK_LIFETIME`/knockout) and DEPTH_CLIP (FSR3 adds the `uShadingChange` sampler) — MV_GEN, LOCK, RECONSTRUCT and RCAS differ only in comments/CRLF. So every switch recompiled (or reloaded a different-keyed disk entry for) four passes that compile to the identical program.
- **Fix**: `ShaderBinaryCache.sourceHash` now hashes the GLSL with comments + whitespace stripped (`normalizeGlsl`). GLSL has no string literals, so the token stream — and the compiled binary — is unchanged; two sources that compile to the same program now share one disk cache entry. Verified: MV_GEN/LOCK/RECONSTRUCT/RCAS normalize to identical hashes across fsr2/fsr3; DEPTH_CLIP and ACCUMULATE keep separate entries (they compile different code). A version switch now pays at most 2 real recompiles (or disk-binary loads) and reuses the rest — and because the disk cache is source-hash keyed, previously cached binaries are found by their new normalized hash automatically (old raw-hash entries are swept).

- **Probe readbacks were all READ_FAIL — glGetTexImage target bug**: the GL 4.3/4.4 fallback passed the texture NAME as the target enum to glGetTexImage/glGetTexLevelParameteri without binding, which is GL_INVALID_ENUM on every call. - **FSR4 restore → 7ms re-suspend cycle (dispatch-failure suspension not grace-gated)**: the world-calm resume can re-arm FSR4 while the GPU queue is still busy (CPU-calm ≠ drained queue), and the first resumed dispatch failing fast instantly re-suspended (log: restored 19:58:17 → suspendedFor=7ms, ~3-6s cycle with Photonics GI bursts). ### FSR4 suspend/resume
- **Iris jitter-blind re-probe oscillation removed ("blinking after a few minutes, only fixed by toggling off/on" fix)**: the Iris jitter probe's periodic re-evaluation (every 60 seconds when the pack was classified as jitter-blind) would clear the blind verdict AND re-arm the probe, so the verdict could flip on each cycle (blind→not-blind→blind...) — each flip toggled jitter between zeroed and active, producing a visible quality blink at the re-probe interval. The re-probe is removed: the one-shot probe (on fresh install or reinit) is sufficient; the blind verdict stays sticky for the session. This was the specific "1.21.11 port only" symptom.
- **FSR4 auto-resume after GPU-saturation suspension:**: on an always-busy iGPU (Voxy/C2ME background meshing) the resume-probe fence may never signal on dense consecutive frames, so FSR4 stayed parked on FSR1 (the visible quality drop the user read as "blinking") for the rest of the session — only a manual off/on (forced reinit) restored it. The suspended-state probe now ALSO resumes on a sustained run of CPU-side calm world frames (10 consecutive frames under the same spike threshold the pre-check uses, gated by the existing min-parked and dimension-hold windows), so a drained-but-fence-gagged queue recovers in ~2s. A 1.5s post-resume grace prevents a single spike frame from instantly re-suspending (the flap that would make the calm-resume useless).
